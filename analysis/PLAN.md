# Implementation plan — improve this release and collect evidence for the next model

**Revision: 30 September 2026.** The user has authorized extensive app telemetry across all consenting installations, central collection, and optional difficulty feedback. This supersedes the original single-device, no-backend and no-rating restrictions for the implementation plan. The six effort coefficients remain fixed. The September 25 local `analysis/REPORT.md` remains a historical single-user audit; its findings do not become population findings because the collection scope changed. The development branch publishes this plan only; the local audit, raw data, figures and reproduction scripts are not included. Existing local audit-script references below describe reusable touchpoints when available, not prerequisites for the VPS checkout: implement equivalent versioned exports/replay from the tracked Swift sources and synthetic fixtures when those scripts are absent. This revision specifies work; no app change, upload, server deployment or release has been performed.

**Purpose. We have competing hypotheses and no established root cause. This update should fix the issues we can justify now, improve difficulty selection where validation supports it, and collect and centrally report enough data for developers to distinguish the remaining explanations. Developers will use that evidence to design, validate and implement a new statistical model in a subsequent release. This update is an improvement and investigation release; it must not be described as the finished difficulty-engine fix.** More observations improve precision and coverage; controlled comparisons are still needed to make causal claims.

**Ordering rationale.** Implement the event contract, offline upload queue, VPS ingestion and data-quality reporting first. Then ship honest service status, abandonment recording, optional feedback before verdict disclosure, and tested generation/timing improvements in the same release. Separate timing epochs and stable experiment assignments keep those changes interpretable. Build anchored skill/bands and solver features in shadow mode; activate only with independent evidence. The audit's 70/73 Zip and 20/20 Patches confidence failures justify examining service decisions immediately, but do not prove insufficient candidate coverage. Preserve P01–P10 IDs; P11–P14 add feedback, central infrastructure, developer research and release management. The numbered activation sequence at the end determines implementation order.

**Design constraints.** Collection covers gameplay in this app on every installation running the update with active consent, including unsuccessful attempts and full candidate pools. Persist the supplied consent state/version; do not invent historical consent dates or install counts. Optional feedback is skippable and precedes every disclosure of the assessed difficulty on invited solves. Keep behavior effort, subjective ratings and model verdicts as distinct fields. Gameplay and local adaptation remain usable offline. Every schema, model, feature, generator, clock and experiment change has a version. Estimates: S ≤1 focused day, M 2–4 days, L 5–10 days including validation; not commitments. All new source files named below are proposed files. The VPS is a proposed host; its capacity, domain, installed services and backup arrangements are UNVERIFIED.

**This update's scope.** Required: P01–P04 instrumentation/metrics and censor capture; P11–P13 feedback, upload/ingestion and developer reporting; P14 controlled rollout; tested P10 selection/budget/fallback fixes and P07 timing cohorts. P08 trace collection and exact feature-redundancy cleanup should be included when correctness/performance gates pass; otherwise log their deferral. P05/P06 anchored calibration/skill, censored model fitting, learned probability recalibration and any pooled statistical model are experimental work, not blockers for shipping useful measurement and supported improvements. Fix as many verified issues as possible, while recording which changes actually ship and why others remain gated.

Store affected cells/edges/rectangles, rule/error reason, monotonic action timestamps, cumulative counters and enough state deltas to reconstruct each attempt. Derive session membership across both games from >30 minutes since last foreground activity, not solve completion; split on resume after that gap. Store selected level before/after each transition. Use `synchronous=FULL` for committed records; WAL alone is not a durability guarantee. Store terminal solve/skip/abandon snapshots durably before updating the JSON snapshot, and reconcile terminal IDs on launch so a crash between those writes cannot create duplicate or missing terminal records. `ProgressStore` retains ownership of saved game state; telemetry does not replace its compatible JSON reader. Batch nonterminal actions for at most 50ms; terminal actions flush before completion acknowledgment. A process failure can still lose actions not yet committed in that interval: log an interrupted capture interval on recovery, with unknown count when unrecoverable, and exclude that attempt from complete-trace claims. Log crash/recovery and sequence gaps explicitly. Extend journal verification to retries, out-of-order arrivals and unknown schemas. See [SQLite WAL durability documentation](https://www.sqlite.org/wal.html).

Collect detailed gameplay for all consented updated installations without silently sampling the candidate pool or losing failed attempts. Old data may be uploaded once under the stated complete-data consent with `origin=legacyImport`, original UUIDs and missing timestamps intact; exclude it from causal/new-policy gates. New installations have no historical backfill. P12 defines durable acknowledgment, bounded disk storage and observable overflow. Performance-related collection losses must generate a loss manifest, never look like complete observations.

**Acceptance.** Replay a fixture with one puzzle per level/game, switch, resume, hint, reset, skip, background, idle hit, solve, and simulated crash. All served puzzles have unique IDs and complete candidate lists; every selected ID occurs in its pool; every new Patches record has creation/visibility/action timestamps when applicable and a terminal timestamp when terminated. No negative durations; no double-counted terminal event after restart; legacy decode preserves unknowns. ## P04 — Log behavior; use genuine lower bounds for censored solves

**P1 · M.** Solves report M; does not translate behavior into invented ratings.

**Exact touchpoints.** `GameController.archiveStatistics/newGame/showStartScreen`, `PatchesController.newPuzzle/commit/changeDifficulty/leave/windowWillClose`; journal from P01. Extend `AdaptiveDifficulty.init(records:)` and `PatchesModel.init(_:)` only after the lower-bound validation gate below; add `CensoredEffortSample` and shared `RidgeObjective`.

**Design.** Define quick replay as next normal puzzle made visible within 15 seconds after a solve, while foreground and same session. A session end is no foreground activity for >30 minutes, recorded retroactively on next launch/resume with `inferred=true`, or explicit application termination; it does not prove dislike. Level change uses P02’s decision definition. Skip is an explicit new-puzzle replacement before solve; abandonment is a discarded nonterminal board (not merely closing/backgrounding or retaining a resumable board). Flush the open thinking interval and capture a terminal snapshot before replacement in both games, including unstarted boards; `reason` is observed UI action, never inferred frustration.

In this release, ship the capture and lower-bound export; fitting censored samples remains independently gated. For complete-from-start telemetry, let `L = min(4, Σ six existing cumulative terms)` at skip/abandon. This is a lower bound on the eventual score **if that attempt continued under the same measurement policy**, because cumulative corrections, pauses, active time, hints and resets never decrease. An unstarted board has L=0 and contributes no useful inequality. Incomplete legacy telemetry, corrupt counters, mixed timing epochs and resumable sessions are not training examples. Quick replay, switch and session end are diagnostic covariates only, not effort labels or rewards.

Keep the completed-solve weighted ridge objective. Add `0.10 × w_i × max(0, L_i − prediction_i)^2` for eligible censored attempts, with total censor weight capped at 10% of completed-solve weight. This is a convex squared-hinge extension of ridge while unclipped linear effort is used in the objective; solve by active-set iteration (≤20 passes, convergence <1e-8) and clip predictions afterward. Persist `censorReason`, L, components, training eligibility, and active-set diagnostics. For the later skill model use `L+θ_at_attempt` in anchored coordinates. Do not update θ from censoring initially: cannot separate difficulty from reason for stopping. Keep this objective shadow-only until it reduces completed-test MAE without worsening all-request matching/coverage.

**Acceptance.** Continuing a captured attempt in fixtures never yields final effort <L; resets keep cumulative counts. Zero-bound samples cannot pull predictions down. Squared-hinge penalty is zero above L and grows below it; completed-only implementation matches current ridge when no censored examples exist. Patches replacement always logs exactly one terminal record before overwriting its session. Compare 60+ future completed tests; activate only if MAE does not worsen >0.01 and no selected-level cohort with ≥15 tests worsens >0.03.

**Risks / rollback.** Informative censoring and more complex fitting; 0.10 cap limits influence but does not remove bias. Separate feature flag permits completed-only ridge immediately. **Dependencies:** P01, P03; P05/P06 only for anchored-coordinate integration.

## P05 — Shared fixed calibration bank and per-installation benchmarks

**P1 · L.** Addresses report D/F’s missing anchor and report E’s weak independent validation. This defines a local operational scale, not a universal human difficulty scale.

**Exact touchpoints.** `Puzzle.make(_:using:)`, `Puzzle.guided` (`Zip.swift:50–194`); `PatchesPuzzle.make/solve` (`Patches.swift:61–130`); `GameController.newGame`, `PatchesController.newPuzzle`; `ProgressStore.AppSnapshot`. Add `CalibrationBank.swift` and `CalibrationState` with per-game versions and timing epochs.

**Design.** Package the same **12 fixed puzzles per game** across installations, four from each low/middle/high structural-prior stratum, with board sizes and distinct geometries represented. Store complete puzzles, seeds, checksums and generator/solver versions in a shared bank manifest. Prior strata are intended coverage; measured coverage must be established centrally. Fixed puzzle IDs connect observations across players and anchor comparisons that randomly generated unique puzzles cannot supply.

During the investigation release, bank service is an optional experiment sharing P09's 10% quota: no consecutive benchmark slots or more than one per session; record scheduling probabilities, request level and exposure number. Benchmark badges do not disclose the app's judgment before P11 feedback. Disabled or incomplete calibration is missing coverage, not a failed player. Feedback invitations may include benchmarks under the same probability/cap rules as other solves.

For the future anchored policy, provisional bank difficulties start at the structural prior, not each installation's first measured solve. P13 estimates and freezes shared D_j values from a development cohort under one timing policy, with per-installation skill effects and a fixed origin constraint; hold out other installations and future sessions for evaluation. Require at least 30 distinct installations, at least 20 distinct-installation observations per bank puzzle, and usable observations spanning intended effort bands before replacing provisional anchors. These are minimum coverage gates, not statistical power guarantees. Freeze a versioned manifest; validate its uncertainty and generalization before bundling it into an app release. No live silent re-estimation from served-level percentages.

Each installation keeps θ for each game. When its first bank pass is complete, initialize `theta = clip(n/(n+8) × weightedMedian(D_j − y_j), −1.5, 1.5)` for n eligible same-clock observations, then use P06 updates. The factor shrinks a sparse skill estimate toward zero; hinted observations receive weight 0.65. Ordinary play works before a full pass and must not wait 120 puzzles for a model migration. Rerun shared bank items sparsely and report memory/exposure effects; keep D_j fixed across users for that version. Never freeze a different intrinsic difficulty scale from each user's first solve and then pool those incompatible scales. Timing changes create separate bank measurement epochs; manifest revisions are explicit.

**Acceptance.** Twelve reproducible unique valid boards/game, intended strata 4/4/4 and stable shared IDs across installations. Optional P11 feedback follows the same pre-verdict rules. Bank coverage and uncertainty are reported centrally; no anchored-policy promotion before the shared cohort and held-out validation gates pass. Rerunning generation from frozen puzzles produces identical IDs. Model/version updates leave frozen D unchanged; new epochs are explicit. Benchmark results include n and exposure number.

**Risks / rollback.** Repetition improves memory, baseline is noisy, and some requested levels may not be available in the bank. Keep benchmark frequency capped and badges honest. Disable scheduling and return to current selection without deleting baseline records. **Dependencies:** P01–P03, P12/P13. Build before P06; use P07 timing epochs.

## P06 — Anchored bands with an explicit per-game skill offset

**P1 · L.** Tests the report F mechanism without claiming report D proved it caused failures.

**Exact touchpoints.** Replace target-quantile blocks in `AdaptiveDifficulty.init` (`AdaptiveDifficulty.swift:83–98`) and `PatchesModel.init` (`Patches.swift:183–192`); update `predict`, `forecast`, `experiencedDifficulty` / `verdict`, and generation snapshot assignment. Add shared `AnchoredDifficultyPolicy.swift`, `SkillState`, `DifficultyPolicyVersion`. Do not change either effort function.

**Design.** Use fixed **experienced-effort** boundaries b=[0.45,0.90] and centers q=[0.25,0.65,1.15], initially matching the current default target midpoints. Let `d(x)` predict effort on the frozen baseline skill scale and θ be current skill (higher means lower experienced effort). Serve with `ŷ = clip(d(x) − θ,0,4)`; target intrinsic difficulty is `q_requested + θ`. Thus improved skill moves the chosen puzzle target upward, while effort-band meaning stays fixed and independent of played-level proportions. Save θ, q, b, model and calibration versions with every served puzzle. Classify completed play against its saved b.

Initialize θ=0 and skill information I=0 before calibration; P05 can initialize θ from the shared bank. This policy remains a shadow/experimental candidate in the investigation release. For each complete, same-epoch solve, obtain **pre-solve frozen** `d_pre(x)` and θ_pre, define `e = clip((d_pre(x) − θ_pre) − y, −0.5, 0.5)`, and update:

```
I_next = 0.98 * I + c
eta = max(0.01, min(0.08, 0.08 / sqrt(1 + I / 20)))
theta_next = clip(theta_pre + eta * c * e, -1.5, 1.5)
```

For a repeated benchmark use fixed D_j in place of d_pre and c=1; for ordinary complete unhinted play c=0.25; hinted play c=0.25×0.65, or 0.65 for a benchmark. No update on invalid/unsolved/mixed-epoch records. Log θ_before/after, e, c and I. This is an Elo-style residual update, **not a claim that effort is a binary Elo outcome**. A positive residual means the player used less effort than expected, so θ rises. Before a shared calibration version is validated, shadow estimates never become production skill updates.

Fit ridge on targets `y_i + theta_at_play_i`, using saved θ_at_play, not today’s θ; this avoids learning recent skill twice. Anchor regression with the 12 frozen D_j and a modest fixed total anchor weight equal to 10% of the normalized completed-solve weight, distributed equally. Keep anchors separate from the 200-solve rolling user buffer. The anchor prior/penalty and offsets must be versioned and validated in P03. If predictions repeatedly clip at 0/4 or θ saturates, log a scale warning and hold the last stable policy rather than silently changing bands.

**Identifiability.** Shared puzzles connect installation-specific skill and intrinsic puzzle difficulty, but the global coordinate origin remains arbitrary: adding a constant to all d and θ leaves d−θ unchanged. Define mean θ=0 in a frozen reference cohort and freeze shared D_j values plus feature/timing versions. Different disconnected puzzle/player cohorts cannot be compared without shared anchors. This identifies an operational population scale; experience, input method, device performance and learning still require analysis. Do not claim universal human difficulty or use all installs' raw effort as interchangeable training labels. P13 evaluates pooled ridge, hierarchical skill models and ordinal feedback alternatives before the subsequent model implementation.

**Acceptance.** Synthetic tests: equal effort distribution with different requested-label mixes leaves b/q exactly unchanged; shifting all true baseline difficulty and θ together preserves predicted effort; repeated easier-than-predicted solves raise θ and move intrinsic target upward; zero residual leaves θ stable. Save/reload is exact. Shadow for ≥60 timestamped tests across ≥6 sessions and all three levels, with ≥15 in each selected-level cohort before per-level claims. Report fixed-bank error, all-request match, qualification coverage and θ trajectory. Activate only if bank MAE does not worsen >0.02 and no adequately sampled selected-level MAE worsens >0.03. No claim of success based only on moving classification labels.

**Risks / rollback.** Model error, memory and motivation can leak into θ; normal-update c and η are deliberately small. Keep current percentile policy accessible by a local developer flag and its state intact. Revert future selection only; never relabel historical solves. **Dependencies:** P01–P03, P05. P07 creates distinct timing epochs; P13/P14 govern promotion with population and temporal validation.

## P08 — Human-style solver traces, a smaller ridge feature budget

**P1 · L.** Addresses report E/I/J’s weak structural signal and verified redundancy. Solver trace features are a hypothesis requiring forward validation, not a promised accuracy gain.

**Exact touchpoints.** `PlayStatistics.extractFeatures` (`Zip.swift:572–597`), `AdaptiveDifficulty.names/vector/prior/init/predict`; `PatchesPuzzle.candidates/solve/features` (`Patches.swift:53–92`), `PatchesModel.prior/init/predict`; generator uniqueness validation. Add `ZipReasoningSolver.swift`, `PatchesReasoningSolver.swift`, `ReasoningTrace.swift`, versioned feature extractor and fixtures. Leave exact existing solvers available for correctness checking, not for leaking solution answers into a human trace.

**Zip tiers.** T1: only-legal continuation to next checkpoint; degree constraints (interior path cells degree two, endpoints degree one); forced edges when remaining required degree equals available edges; reject edges violating checkpoint order. T2: premature-loop prevention, disconnected unvisited-region exclusion, articulation/cut-set connectivity implications and checkpoint reachability pruning; every rule must be sound under the Hamiltonian-path and ordered-clue constraints. T3: try each unresolved edge and run T1/T2 to contradiction (one assumption); eliminate only proven contradictions. T4: bounded branching after T3 is stuck, depth 2–4 with deterministic ordering, ≤10,000 nodes or 100ms. Exhaustion means unknown difficulty/censored trace, not a proof of uniqueness. Trace never consults `puzzle.solution`.

**Patches tiers.** T1: enumerate legal rectangles from visible clues; place a clue’s sole candidate or a rectangle forced because an uncovered cell has only one remaining covering candidate; propagate overlap exclusions. T2: common-cell intersections of all candidates of a clue forbid competing rectangles that cover those cells; propagate locked coverage and disconnected uncovered-region impossibility using explicit exact-cover constraints. T3: one rectangle assumption followed by T1/T2 propagation; eliminate only contradictions. T4: minimum-remaining-values bounded search, depth 2–4, same time/node budgets. Existing uniqueness solver validates solutions independently; do not turn a budget timeout into a high tier “solved” claim.

Persist highest tier actually used, successful steps per tier, share of board determined by T1, number of stalls, branching choices at stalls (mean/max), deepest successful/attempted lookahead, nodes, time, completed Bool and exhausted Bool. Define a step as one logged rule application with stable affected cells/edges, not recursion count. Deterministic tie-breaking by cell/rectangle coordinates and canonical edge order makes features reproducible. Timeout flags and lower-bound depth are explicit; never impute max difficulty on timeout.

**Retirements and model budget.** Zip forced-cell density is exactly redundant with junction density and intercept: remove it from the learned feature vector, while preserving its contribution in the structural-prior algebra (substitute `1−junctionDensity`) so removal alone does not change prior behavior. Checkpoint-gap spread is zero in this sample: remove from the active fit but keep in logs and re-enable only after variance and forward evidence. Other geometry features are not proven useless; retain in logs, replace only via predeclared forward ablations. Patches has no proven constant/redundant base feature, so no automatic retirement yet.

Keep ridge as this release's production baseline. The subsequent statistical model is chosen through P13 evidence; do not precommit it to the same family. Standardize new trace features using training-only means/SD, clip transformed values to ±3; preserve intercept. Candidate seven-feature set: board cells, highest tier, log1p(total rule steps), T1 share, log1p(stall count), mean branching at stall, lookahead depth; tier-step counts remain available for later substitution, not an immediate expansion. Use `p ≤ min(8, floor(n_eff/15))` non-intercept coefficients, including interactions; `n_eff=(Σw)^2/Σw²`. Below n_eff=30 fit intercept correction only. Select a fixed feature priority list on a development prefix; evaluate the remaining chronological suffix once. Permit at most one prespecified interaction (stall count × branching), only within that budget and with forward improvement.

Preserve recency 60, max 200, hint multiplier 0.65. For standardized features use default λ=0.02 and intercept λ=0.001; select among {0.005,0.02,0.08} only with nested forward folds entirely inside each training window and ≥60 training examples. Do not tune and report on the same outer tests. Changing feature scaling means the old penalty is not numerically equivalent; keep the old model as an explicit baseline.

**Acceptance.** Every sound-rule application passes property tests against the existing exact solver on 1,000 seeded valid boards/game; incomplete traces cannot label a puzzle solved. At least 95% finish within 100ms across the supported test-machine set, else retain trace as offline diagnostics only. Feature generation is identical across repeated runs. Native/vector parity tests and exact redundancy checks pass. On ≥60 new outer tests, accept feature replacement only if MAE improves ≥0.02, prior/old model comparisons use identical IDs, and no selected-level cohort with n≥15 worsens >0.03. If not, keep existing ridge and log features for more evidence.

**Risks / rollback.** Solver rule unsoundness, expensive generation, machine difficulty unlike human reasoning, and cold-start dimensionality. Feature version flag reverts prediction to legacy vector; never discard trace logs. **Dependencies:** P01, P03, P07; integrate anchored coordinates from P06.

## P11 — Optional difficulty feedback before the app's judgment

**P0 · M.** Adds independent subjective evidence while preserving the distinction between reported difficulty and measured effort.

**Exact touchpoints.** `GameController`'s `board.onWin` closure and `archiveStatistics` in `Zip.swift`; `PatchesController.commit` and `showStatistics` in `PatchesUI.swift`; `DifficultyToast.show`; both statistics screens. Add shared `DifficultyFeedbackView.swift`, `FeedbackState`, and a presentation coordinator. Extend the P01 journal; the solve remains complete even when the user gives no feedback.

**Presentation contract.** Freeze and durably record the objective effort and model verdict at solve time, without presenting the verdict. For invited solves, show “How difficult did this puzzle feel?” with an ordered five-point scale: Very easy / Easy / Moderate / Hard / Very hard, plus “Skip” and “Stop asking.” No default answer, model-colored choices, agreement question, or repetition after dismissal. Neutral completion text may say “Solved”; it must not reveal assessed difficulty. `solved → feedbackPending → submitted|skipped → verdictShown` is the only allowed invited-solve sequence. Submission or skip resolves locally and immediately reveals the saved verdict, independent of connectivity. Next-puzzle, library navigation, statistics, and window close resolve pending feedback as skipped before any verdict disclosure; closing need not display a toast. Gate statistics cells, accessibility announcements, success text, toast colors, and restored completion views as well as the toast itself. Persist the pending state: after a restart either resume the question before disclosure or record a recovery skip; never ask after a verdict was already shown. No retroactive survey of old solves.

**Invitation policy.** Initial default: deterministic random invitation with probability 0.25 per served puzzle, decided before its outcome is known, capped at three displayed invitations per session and six per local calendar day. Store the random draw, cap state, effective eligibility/probability, policy version, and suppression reason. Display only on solve; unsolved attempts still receive complete behavioral telemetry. “Stop asking” disables invitations until re-enabled in settings, without disabling consented telemetry. Keep the probability configurable and versioned; benchmark/exploration solves use the same policy. These caps limit survey burden, not gameplay collection. Record `invitedAt`, `submittedAt`, `skippedAt`, `verdictShownAt`, response ordinal, response latency, prompt/scale version, presentation order, requested level, prior exposure, hint usage, and whether the pre-verdict contract was satisfied. Missing, suppressed, skipped, and answered are separate states; none means Moderate.

**Value and bias.** Treat ratings as an ordinal secondary outcome, not a numeric replacement for the six-term effort score. Requested labels, prior verdicts, hints, frustration, personal scale usage, and voluntary response can bias ratings even when the current verdict is hidden. Report response rates and rating distributions by game, installation, requested level, experience, assistance, and timing/experiment cohort. Compare respondents with eligible nonrespondents on observed behavior; never claim invitation randomization removes nonresponse bias. Prompt wording and order can influence answers, motivating the fixed neutral scale and pre-verdict requirement. [Survey design and order effects](https://www.pewresearch.org/writing-survey-questions/).

In this release feedback informs developer diagnostics and experiment decisions; it does not directly refit the production effort model. P13 can test an ordinal auxiliary model with installation-specific response thresholds and partial pooling. If combining its loss with an effort objective later, normalize both on training data and evaluate prespecified auxiliary weights `{0, 0.05, 0.10}` inside development folds; zero is a required baseline. These are trial settings, not empirically established reliability weights. Do not equate ordinal steps with equal effort distances. Require prospective benefit on both behavioral and subjective outcomes, with responder/nonresponder sensitivity analyses, before giving ratings production influence. Small samples shrink toward the population response distribution; frequent responders cannot dominate through solve counts alone.

**Acceptance.** In both games, test mouse, keyboard, screen-reader, hint-completed solve, statistics navigation, next puzzle, offline submission, close/relaunch, and duplicate callbacks. Every answered rating precedes `verdictShown` in persisted sequence; no presentation path leaks the assessed verdict while pending. Exactly one response or skip per solve, no answer required to continue, and no production label changed by feedback. Scheduler fixtures reproduce probability/caps and disabled-state behavior. P13 reports missingness and bias alongside every subjective result.

**Risks / rollback.** Survey fatigue, residual anchoring, selective response, and prompt-induced changes in replay behavior. Disable invitations independently while preserving already captured answers and verdict-order metadata. **Dependencies:** P01/P02; P12 for upload, P13 for interpretation. Feedback does not wait for the new statistical model.

## P12 — Central collection, with the VPS as the proposed host

**P0 · L.** Makes all updated, consenting installations contribute to one inspectable dataset, while keeping gameplay and adaptation usable offline.

**Proposed architecture.** `macOS app → local SQLite events/outbox → HTTPS collector → PostgreSQL raw events → versioned analytical tables → developer reports`. Prefer a small Python/FastAPI collector, Caddy for HTTPS, and PostgreSQL on the user's VPS as the initial implementation: Python matches the existing analysis tooling, and a relational store supports constraints, deduplication, joins and append-only event payloads. This is a proposed deployment, not a claim about currently installed services. Pin supported versions and migrations when implementation begins. There is no need for Kafka, a separate warehouse, or a public dashboard at this stage. [FastAPI documentation](https://fastapi.tiangolo.com/tutorial/) and [Caddy HTTPS documentation](https://caddyserver.com/docs/automatic-https) support the proposed components.

**Tradeoff and hosting gate.** VPS advantages: direct control, existing infrastructure, and straightforward database access. Costs: a single failure domain, operational work, and unknown storage/backup capacity. Before deploying, record VPS OS, CPU/RAM, free disk, existing workloads, domain/TLS route, backup destination, retention settings, and projected install/activity range in `server/DEPLOYMENT.md`. Run a staging load test before selecting limits. If capacity or reliable backups fail the gate, retain the same HTTPS/event contract and use a separate or managed PostgreSQL host; local app work can continue. Hostname and credentials are implementation inputs, not reasons to postpone editing this plan. No server access or deployment has been performed for this revision.

**Exact touchpoints / proposed artifacts.** Add `TelemetryUploader.swift`, `TelemetryCredentials.swift`, `TelemetryUploadStatus`, journal/outbox migration and `build.sh` inputs (`-lsqlite3` for direct SQLite use). Add `server/collector/`, `server/migrations/`, `server/tests/`, `server/DEPLOYMENT.md`, locked Python dependencies, and staging/production configuration examples without secrets. Wire upload on launch, connectivity recovery, periodic foreground idle, and durable terminal batches; do not start a network operation for every pointer event. Use `URLSession` with persisted batch files and explicit restart recovery. OS scheduling is not a promise of immediate delivery. [Apple URLSession background configuration](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:)).

**Identity and trust.** Persist a random installation UUID and per-installation credential in Keychain; a reinstallation can create a new identity and must not be interpreted as a new person with certainty. Enrollment is rate-limited and returns a server-bound credential; never embed a shared write/admin secret in the app. Support credential rotation without changing event IDs. Public enrollment and credentials authenticate a submission identity, not an untampered app or a truthful human: validate telemetry, flag suspicious sequences and exclude them from model gates. Database ports remain private; developer reads use a separate read-only role over SSH/VPN or an authenticated report endpoint. Record consent version/status supplied by the app under the stated consent; do not prompt existing consenting users again merely to implement this authorization. A later consent change stops future collection/upload according to that recorded state.

**Ingestion contract.** Proposed endpoints: `POST /v1/installations`, `POST /v1/events/batch`, and authenticated developer dataset/report access. The batch carries `batchID`, installation, schema version, event count and payload checksum; events retain their immutable P01 IDs/sequence. Initial limits: ≤500 events, ≤512 KiB compressed and ≤4 MiB decompressed per batch, including bounded candidate-pool chunks for large decisions. A decision manifest declares expected chunks/candidate counts; incomplete pools are never silently treated as complete. Limits are provisional until measured. Store client timestamps and server `receivedAt` separately; arrival order is not play order.

Persist accepted events and receipt metadata in one database transaction; acknowledge specific accepted or already-identical event IDs **only after durable commit**. Use uniqueness on `(installation_id,event_id)` and `(installation_id,sequence)` for new journal events, canonical payload hashes, and `ON CONFLICT` handling. Identical retries return acknowledgment; an ID/sequence collision with different content is quarantined and never overwrites the original. Valid events in a mixed batch can commit with explicit per-event accepted/rejected/retryable results. Persist rejection metadata sufficient to investigate errors; the app keeps rejected records in a local quarantine until a repair or recorded disposition. Unknown schemas produce an upgrade/quarantine response, not a successful empty acknowledgment. Pin `fsync=on` and `synchronous_commit=on`; receipt acknowledgment must not depend on an in-memory worker or deferred analytical transformation. PostgreSQL supports conflict handling, but application checksum checks and transaction boundaries define this protocol. [INSERT conflict handling](https://www.postgresql.org/docs/current/sql-insert.html), [WAL durability settings](https://www.postgresql.org/docs/current/runtime-config-wal.html).

**Retry and storage.** Delivery is at least once; the server deduplicates events. Use exponential backoff with full jitter, beginning around five seconds and capped at one hour; obey `Retry-After` for 429/503. A lost response after commit is a normal retry case. Recover/re-enroll or rotate on authentication failure without discarding the outbox; split 413 batches; quarantine permanently invalid records instead of retrying forever. Network, analytics or collector failure must not block solve completion. Delete acknowledged outbox entries transactionally only after their matching receipt. Retain the underlying local journal for 30 days after acknowledgment for debugging, subject to a measured total disk cap.

Default unacknowledged-data cap: 256 MiB per installation, configurable after measurement; reserve 4 MiB for loss/recovery manifests and terminal summaries. Warn in developer upload status at 80%. If offline data exceeds the cap, evict oldest unacknowledged nonterminal payloads only with a durable manifest listing IDs/sequence ranges, types, bytes, affected attempts and reason. If even terminal capacity is exhausted, record a bounded summary of lost terminal ranges; never claim a gap-free dataset. Attempts with loss are excluded from complete-trace/model gates. Complete collection is the normal target across all installations; prolonged outages, disk failure and bounded queues are explicit coverage limitations. Do not silently switch to sampling under load. Remote kill switches may stop defective capture, but must record the resulting collection gap.

**Database and operations.** Keep append-only raw payloads, receipts, installations/consent history, quarantine/loss records and experiment assignments. Derived `serves`, `candidate_decisions`, `candidates`, `attempts`, `feedback`, `sessions` and `model_runs` retain source event IDs and transformation versions; rebuild them idempotently. Index installation/sequence, serveID, game/time/version and puzzleID. Normalize frequently queried dimensions while preserving JSON payloads. Legacy imports keep original record IDs and unknown fields; deduplicate with `(installation,game,legacyRecordID,origin)` and report revisions, never invent event chronology.

Proposed initial retention: 180 days of detailed central events/candidates, 365 days of derived summaries, with frozen, access-controlled research snapshots retained for reproducibility under a documented review schedule. Retention deletions are recorded in report manifests. Size from measured activity, not install count alone: `daily bytes = active installations × serves/day × (events/serve × bytes/event + candidate bytes/serve)`. Illustration only: 1,000 active installs × 10 serves × 300 events × 600 bytes is **1.8 GB/day**, or **324 GB/180 days**, before candidate pools, indexes and backups. This could exceed a small VPS; measure 100 representative serves per game and forecast disk/network headroom before rollout.

Monitor accepted/rejected/duplicate events, sequence gaps, late arrivals, incomplete pools, oldest pending age, batch latency, database errors, disk growth and report freshness. Alerts go to developer operations, not players. Start with hourly encrypted off-host database backups plus WAL archiving where configured; target recovery point ≤1 hour and recovery time ≤4 hours, proven by a restore drill. Local retries do not recover data already acknowledged and lost on the server. Keep query/report workloads off the ingestion transaction path; throttle jobs or add a read replica only when measured contention warrants it. [PostgreSQL backup approaches](https://www.postgresql.org/docs/current/backup.html).

**Acceptance.** Three staging installations submit both games while online/offline, then restart and retry. For at least 100 complete attempts, reconcile local IDs and payload hashes with central raw events, full pools, terminal summaries and report counts. Simulate lost acknowledgments, duplicate/concurrent batches, clock skew, out-of-order chunks, 401/413/429/503, schema errors, queue overflow, collector/database restart and backup restore. No acknowledged committed event is duplicated or silently overwritten; gaps and quarantine remain visible. Load-test at twice the declared launch peak for 30 minutes, with p95 receipt latency ≤2s and no unexplained loss, while representative play still meets P01 UI overhead gates. Publish measured capacity and recovery results; a failure prevents broad central rollout, not offline play.

**Risks / rollback.** Storage growth, forged submissions, operational outages and shared-VPS contention. Disable uploads independently and keep bounded local capture/outbox; preserve compatible schemas and data for retry. Hosting migration changes the endpoint/configuration, not event identity or research semantics. **Dependencies:** P01; P13/P14 consume central data. No new model is needed to start collection.

| Hypothesis | New evidence and comparison | Decision it informs |
| --- | --- | --- |
| Selection bypass, candidate scarcity or conservative forecasts | Full pools distinguish qualifying-but-unselected, none-qualified, eligibility conflict and poorly calibrated probabilities; replay baseline and P10 on identical frozen states, then a stable live comparison | Repair selection first; expand generation only when coverage limits are demonstrated; recalibrate probability only with held-out outcomes |
